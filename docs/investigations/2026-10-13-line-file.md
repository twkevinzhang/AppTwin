# LINE 傳送檔案選取 crash 調查

使用者描述：openinfo/user2 的 cloned LINE，在指定聊天「張震龍 Kevin」左下角＋→傳送檔案→點選檔案時 crash。使用者已完全授權繼續調查，包括無私人資料 fixture 的選取與可能傳送。主代理唯一 ADB 執行者；本文件前段保留 v1016 調查紀錄，後段記錄後續已授權修正與 v1020 實機驗收。

## 實機事實

ASUS Zenfone7/API31，安裝AppTwin1016。原聊天＋選單的「檔案」開啟系統 `com.google.android.documentsui/com.android.documentsui.picker.PickActivity`，action=`GET_CONTENT`。物理Activitystack沒有TrustedUriPickerActivity，亦沒有ChooserActivity。未輸出Intent extras、私人檔名或URI。

建立67-byte測試文字檔，只含AppTwin測試標記，放在Download。經即時focused accessibility window定位確切owned檔名後點選（沒有點私人文件）。2026-10-13 17:41:21.981，LINE guest PID18312主執行緒crash，堆疊 `ContentResolver.query -> ProviderHook.invoke:244 -> enforceSpaceAccess:154`，與17:15舊樣本相同。GuestCrashReplayException會移除原始message，但此throw site的源碼只有selected URI授權拒絕。

server selected-uri-grants.bin在選取前後都是SUR1 header＋count0（8bytes），hash相同，沒有任何選取授權被登記。没有以manual grant、URI白名單或整個provider放行修改結果。未另點傳送button；因query立即崩潰，沒有完成傳送的證據。

## 根因與尚未判定的分支

直接原因已實機證明：系統選擇器可回傳文件，但AppTwin沒有為該Space/package登記選取URI。LINE query文件metadata時，精確Space URI gate拒絕，例外未被LINE捕捉，因此guest崩潰。可靠度分數99%。驗證方式：可信picker完成後帳本應精確登記該user/package/URI，原query與檔案流程成功；未選URI與其他Space仍拒絕。

更上游「為何沒走bridge」尚未完全定位。AM StartActivity537只在resultTo!=null且頂層OPEN_DOCUMENT／GET_CONTENT／PICK_IMAGES才bridge；ChooserActivity→ResolverActivity的external startActivity可能漏bridge，null resultTo／其他launch API／cached interface bypass亦可能。此次stack沒有chooser，不能斷言chooser就是原因。ArrayUtils.indexOfObject(args,IBinder.class,2)是從index2查找，非第二個binder，不能據此認定signature解析錯誤。下一階段如實作診斷，應只記method/action/resultTo存在/requestCode/route與prepare/take/complete/accepted，避免URI/內容或extras。

修正方向：令實際guest文件picker路徑都由trusted host session完成選取與精確grant登記，再向同一guest activity回傳；不得改為只要host持有grant就讓所有Space讀取，不得移除Provider gate。需涵蓋原檔案選取query、讀取、取消、重試、其他Space隔離與未選URI拒絕；若允許傳送，另確認測試檔送達，不能以query成功代替傳送成功。

## 修正與 2026-10-13 ASUS v1020 驗收

### 已定位原因與修正

v1017 的有界 metadata 診斷證明，LINE 實際呼叫為一層 `ACTION_CHOOSER` 包住文件 picker，且原 result token 存在。原 StartActivity hook 只辨識頂層 picker action，因此漏接 chooser；這解釋了系統 picker 能回傳、Space ledger 卻為零。修正以 `UriPickerRequestPolicy` 解出一層合法 chooser 主 picker，由可信 host picker 完成；原 framework token、resultWho、requestCode 與 options 保留。GET_CONTENT 語意不變，不製造永久系統授權。

server 再次解析與驗證真實 calling PID、user/package 與 activity token ownership，成功結果所有 content URI 均須有真實 host read grant，再登記 exact user/package/URI。取消不新增授權，失敗回 RESULT_CANCELED，重試建立新 session。nested、malformed、initial-intents 與 host-component chooser 不走新 bridge。Provider gate 未放寬。

觀察事實：原始 v1016 query 在精確 URI gate 崩潰；v1017 chooser route 已確認；v1020 原操作與 host-positive/other-Space-negative 實機通過。結論：此次檔案選取 crash 的授權路由缺口已修正。可靠度分數：99%。驗證方式：在指定 LINE 聊天重跑原＋→檔案→選取、取消與重試；其他 Space 必須無法查詢或開啟同一 URI。

### 原生 hook 的必要修正

驗收途中另遇 ARM64 啟動 SIGILL，涉及原 inline hook 遠跳的多指令入口改寫；不能把它算成 picker 測試成功。安全候選 v1019 找不到可用近端 island 時，敏感 Binder gate 仍拒絕啟動，沒有降級繞過邊界。

v1020 改以 `/proc/self/maps` 的實際空隙、有界 MAP_FIXED_NOREPLACE 配置近端 island。code page 預建 stub 並一次轉 RX，後續只 release-store 至穩定 RW target slot，stub acquire-load；原函式入口僅以單個對齊 4-byte atomic CAS 發布 branch。published slot 永不重用，資源、查圖、配置次數與 deadline 均有上限；失敗維持 fail closed，沒有 MAP_FIXED 覆蓋或恢復不安全遠跳。

非作者唯讀 native review 未發現 blocker；五組 standalone native tests 通過。ASUS 原有共享媒體 WRITE 六階段嚴格測試 32.457 秒 PASS，包含實際 guest native/Provider/relative path 讀寫、撤權與其他 Space 隔離。這支持已測執行路徑；不宣稱所有裝置或所有 native 啟動競態均已窮盡。
